# Design: Chapter Batch Import Workspace Gap Closure

**日期**: 2026-05-24  
**状态**: 待评审  
**关联设计**: [2026-05-24-chapter-batch-import-design.md](./2026-05-24-chapter-batch-import-design.md)

## 目标

这份补充设计只处理当前实现评审中确认的缺口，不重写原始 Chapter 批量导入工作台设计，也不扩大业务范围。

本轮补完聚焦三件事：

1. 把“保存确认”和“是否立即执行”真正解耦。
2. 把“只能编辑草稿状态条款”落实成明确的界面与状态约束。
3. 补齐文档级和条款级状态语义，保证结果页和续跑行为一致。

## 背景

当前模块的主体能力已经具备：

- 文档导入后可统一选择 `章节` 或 `条款` 并自动拆分。
- 工作台按文档管理，支持双击打开右侧抽屉。
- 抽屉支持文档级公共字段确认、条款级字段编辑、重复提示、本地状态持久化。
- 执行器支持文档级串行、条款级创建和上传、失败重试、跳过和恢复。

但实现和已确认需求之间还有三处偏差：

1. 抽屉里同时出现 `保存确认`、`直接上传`、`稍后处理` 三个动作按钮，且三者实际走的是同一条保存逻辑，交互语义不成立。
2. 条款编辑权限没有按照“仅草稿可编辑”收紧。
3. 状态机虽然基本可用，但对“上传中”“部分完成”“取消后恢复”的工作台语义还不够明确。

## 设计范围

本补充设计只覆盖以下内容：

- 抽屉底部动作区和确认后分流窗口
- 条款级编辑权限
- 文档级和条款级状态语义
- 结果页中的动作可见性与禁用规则

本补充设计不覆盖以下内容：

- 后端接口变更
- 拆分算法调整
- 目录树推导规则重做
- OnlyOffice 在线打开能力
- 自动修改已拆分 docx 内容

## 设计一：确认与执行交互

### 抽屉动作区

右侧抽屉底部只保留一个主按钮：

- `保存确认`

移除当前并列的：

- `直接上传`
- `稍后处理`

这样做的目的，是把“确认数据正确”和“是否立即执行”分成两个顺序步骤，而不是让抽屉底部承担两个层级的决策。

### 保存确认流程

用户点击 `保存确认` 后，系统按顺序执行：

1. 校验当前参与确认的文档级必填字段。
2. 保存当前抽屉中的文档级和条款级本地编辑结果。
3. 对疑似重复条款逐条弹窗，让用户选择：
   - `仍然创建`
   - `跳过此条`
   - `取消本次确认`
4. 当重复处理完成后，再弹出一个二次决策窗口，让用户选择：
   - `直接上传`
   - `稍后处理`
   - `取消`

### 二次决策窗口语义

#### 选择 `直接上传`

- 当前文档或当前批量确认的文档进入执行队列。
- 队列按当前列表显示顺序串行执行。
- 文档状态从 `待创建` 或 `待上传` 进入 `创建中` / `上传中`。

#### 选择 `稍后处理`

- 只保存本地记录，不进入执行队列。
- 文档停留在：
  - `待创建`，如果还没有任何 chapter ID
  - `待上传`，如果已经有 chapter ID 但还未上传完 docx

#### 选择 `取消`

- 本次保存前已经写入的本地表单修改仍然保留。
- 不自动入队。
- 不影响其他文档。

### 取消边界

以下两类取消都必须是“本地编辑保留、执行不启动”：

- 重复提示阶段用户取消
- 二次决策窗口阶段用户取消

这保证用户不会因为临时不想执行而丢失已经整理好的表单内容。

## 设计二：仅草稿可编辑

### 约束对象

本约束只作用于条款级差异字段：

- `条款编号`
- `测试内容`

文档级公共字段仍允许在非执行中状态下编辑。执行中的文档整体只读。

### 编辑性判定规则

按“是否已有后端 chapter”和“后端状态”联合判定：

| 条款状态 | 是否可编辑 | 说明 |
| --- | --- | --- |
| 尚未创建成功 | 可编辑 | 包括 `待创建`、`创建失败` |
| 已创建成功且后端状态为草稿 | 可编辑 | 符合“仅草稿可编辑” |
| 已创建成功且后端状态不是草稿 | 只读 | 允许查看和重试上传，不允许改字段 |
| 已创建成功但后端状态未知 | 只读 | 采用保守规则，避免误改非草稿条款 |

### 上传失败场景

如果条款已经创建成功，只是 docx 上传失败：

- 当后端状态仍是草稿时，允许继续改 `条款编号` 和 `测试内容`
- 当后端状态不是草稿或未知时，只允许重试上传，不允许再改字段

### UI 行为

#### 可编辑条款

- `条款编号`
- `测试内容`

保持可输入状态。

#### 只读条款

- 两个字段都禁用编辑
- 错误信息列或状态提示中显示原因，例如：
  - `后端非草稿，禁止编辑`
  - `后端状态未知，禁止编辑`

#### 执行中的文档

当文档处于 `创建中` 或 `上传中`：

- 文档级公共字段只读
- 条款级表格只读
- 仅保留查看类或取消类动作

### 与 docx 内容解耦

无论用户是否修改条款字段：

- 都继续沿用原先拆分出的 docx
- 不自动改写 docx 内容

这条规则保持不变。

## 设计三：状态机与结果页补完

### 文档级状态

工作台文档级状态定义如下：

| 状态 | 语义 |
| --- | --- |
| `待确认` | 刚拆分完成，等待用户确认表单 |
| `待创建` | 确认已保存，但尚未创建任何后端 chapter |
| `创建中` | 当前文档正在逐条创建 chapter |
| `待上传` | 至少已有一个条款拿到 chapter ID，但 docx 尚未全部上传 |
| `上传中` | 当前文档正在逐条上传 docx |
| `部分完成` | 已有部分条款上传成功，但并非全部成功 |
| `失败` | 本轮尝试没有任何上传成功，且已产生创建失败或上传失败 |
| `已完成` | 全部条款上传成功 |

### 条款级状态

条款级状态保持为：

| 状态 | 语义 |
| --- | --- |
| `待创建` | 尚未创建 chapter |
| `创建失败` | chapter 创建失败，可重试 |
| `待上传` | chapter 已创建，等待上传 docx |
| `上传失败` | docx 上传失败，可重试 |
| `上传成功` | docx 已上传成功 |
| `用户跳过` | 用户显式选择跳过该条 |

### 取消与恢复

#### 取消执行

- 只允许取消当前正在执行队列中的文档。
- 取消后不继续后续文档。
- 已成功的条款保持成功。
- 尚未处理的条款保持原状态。

#### 取消后的文档聚合状态

取消不是一个新的终态。取消后文档应重新聚合为以下之一：

- `待创建`
- `待上传`
- `部分完成`
- `失败`

这样后续才能从当前状态继续，而不是进入一个无法续跑的特殊状态。

### 续跑规则

手动再次执行时，系统自动从当前条款状态继续：

- `待创建` 继续创建
- `待上传` 继续上传
- `创建失败` 在用户选择重试后重新创建
- `上传失败` 在用户选择重试后重新上传
- `上传成功` 不重复处理
- `用户跳过` 保持跳过，除非用户手动恢复

### 结果页与工作台动作

结果页仍沿用当前独立工作台，不新增新页面。

#### 文档级右键动作

- `打开详情`
- `重新拆分`
- `取消执行`
- `删除记录`

#### 条款级右键动作

- `重试创建`
- `重试上传`
- `跳过此条`
- `恢复跳过`
- `打开本地 docx`
- `打开后端 chapter 记录`

### 删除语义

删除规则保持为：

- 只删除整个文档的本地记录
- 不删除单条条款记录
- 不删除后端 chapter
- 不删除后端 docx
- 不删除原始本地源文件

执行中的文档必须先取消，之后才能删除。

## 对当前实现的影响

如果按本设计补完，现有实现需要至少做以下调整：

1. 抽屉动作区改为单主按钮。
2. 新增保存后的二次决策窗口，并允许取消。
3. 条款表格按 `chapter_id + backend_chapter_status` 控制编辑性。
4. 文档执行中抽屉整体只读。
5. 状态聚合逻辑以“取消后继续可执行”为目标重新收口。

## 验收标准

满足以下条件时，本轮缺口补完视为完成：

1. 抽屉底部只保留 `保存确认`。
2. `保存确认` 后必然弹出 `直接上传 / 稍后处理 / 取消` 的二次决策窗口。
3. 条款级编辑仅在“未创建成功”或“后端草稿”时可用。
4. 后端状态未知时按只读处理。
5. 执行中的文档抽屉整体只读。
6. 取消后文档仍能从当前状态继续，而不是进入不可续跑状态。
7. 删除动作始终只删除本地整篇文档记录，不影响后端。

## 风险与约束

- 本设计依赖本地记录中的 `backend_chapter_status` 作为条款可编辑性的唯一后端状态依据。
- 如果后端没有在后续查询中持续返回最新状态，界面必须继续采用“未知即只读”的保守策略。
- 本设计不包含真实服务器联调和生产数据回收策略。
