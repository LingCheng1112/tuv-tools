# Design: Splitter 定点修复方案

**日期**: 2026-05-26  
**状态**: 已确认

## 概述

本设计用于修复当前 DOCX splitter 在真实样本中暴露出的 4 个明确问题：

1. `run` 内混排的 metadata 前缀没有被正确去除
2. 清洗后表格外边框恢复错误，左右粗边污染到内部列线
3. 导出块构建逻辑额外插入空段，导致同一条款内部版式变松
4. Annex 版本导出时，修订历史表的识别条件过宽，存在误删正常表格的风险

这轮修复是**定点补丁**，目标是把上述 4 个问题精确修掉，不改变现有条款识别规则、不扩大清洗规则范围、不重构 splitter 主流程。

## 设计范围

### 本次包含

- 修复 `19.112` 这类条款中 `Equipment : sample ID:` 与真实测试内容混排时的清洗行为
- 修复 `15.1 / 15.2` 这类被拆开的表格在清洗后外圈边框恢复错误的问题
- 回退导出块拼装时新增的空段副作用，恢复旧版 section 间空段语义
- 将 Annex 修订历史清理改成“标题 + 紧邻表格”的联合判定
- 补齐与这 4 个问题直接对应的单元测试
- 使用现有真实样本做导出验证

### 本次不包含

- 不修改 [parsing.py](O:/tuv-tools/src/tuv_tools/core/splitter/parsing.py) 的条款识别主规则
- 不修改清洗规则配置文件
- 不扩大到更多历史真实文档做回归基线
- 不顺带重构 splitter 架构或抽象新的文档规范化层
- 不处理 review 之外的其他潜在优化点

## 目标与非目标

### 目标

- 对真实样本中的异常路径做最小范围修正
- 保证清洗后的测试正文保留，不因 metadata 清理误伤真实内容
- 保证表格仅恢复最外圈边框，不新增内部粗边
- 保证导出文档在版式上不新增统一性空白副作用
- 保证 Annex 正常内容不会再因宽松修订表识别被误删

### 非目标

- 不追求这轮代码结构最优
- 不为未来所有文档形态设计通用框架
- 不把这轮问题扩展为全量 splitter 语义升级

## 方案比较

### 方案 1：定点修补当前链路（推荐）

仅在 [cleaning.py](O:/tuv-tools/src/tuv_tools/core/splitter/cleaning.py) 和 [exporting.py](O:/tuv-tools/src/tuv_tools/core/splitter/exporting.py) 内修复对应缺陷，并在 [test_splitter.py](O:/tuv-tools/tests/test_splitter.py) 增补最小回归测试。

优点：

- 行为漂移最小
- 与“只修 4 个问题”的边界最一致
- 回归面清晰，真实样本验证路径明确

代价：

- 代码结构不会显著变优雅
- 需要在现有职责边界内做较细的补丁式处理

### 方案 2：轻量重组清洗/导出阶段

把前缀裁剪、边框恢复、版本过滤分别抽成新的处理步骤。

优点：

- 结构更清楚
- 后续扩展更容易

代价：

- 触碰更多调用路径
- 容易引入与本轮目标无关的行为漂移

### 方案 3：重建更通用的文档规范化层

在 run、表格边框和版本导出之上增加统一抽象后再生成文档。

优点：

- 长期结构最完整

代价：

- 明显超出本轮范围
- 与“紧急修异常、禁止扩散”的目标冲突

### 结论

采用**方案 1：定点修补当前链路**。

## 详细设计

### 1. `run` 内 metadata 前缀裁剪

#### 问题

当前清洗逻辑以“整个 `run` 被命中范围完全覆盖才删除”为主。对于真实样本 `19.112` 里这种情况：

`19.112 Abnormal operation Equipment : sample ID: tests specified in Cl. 11 ...`

如果 `Equipment : sample ID:` 和后面的真实测试内容位于同一段、甚至同一 `run` 内，现有逻辑不会把前缀精确去掉，只能保留整段原文，导致脏 metadata 残留。

#### 设计

在现有段落清洗路径中增加一个**更窄的前缀裁剪能力**：

- 只处理已经被识别为 metadata 的片段
- 只裁掉命中区间本身
- 尽量原地修改 `w:t` 文本节点内容
- 不重建整段 paragraph
- 不放宽整行/整段删除条件

实现上，按可见字符区间定位 metadata 片段，把命中区间映射回具体文本节点，仅对对应文本做裁剪。这样可以在保留原有 `w:rPr`、字体、粗细、语言属性的前提下，去掉中间的脏前缀。

#### 成功结果

真实目标输出应从：

`19.112 Abnormal operation Equipment : sample ID: tests specified in Cl. 11 ...`

变为：

`19.112 Abnormal operation tests specified in Cl. 11 ...`

并且 `tests specified in Cl. 11 ...` 后续正文必须保留。

### 2. 外圈边框恢复范围收窄

#### 问题

当前外边框恢复逻辑会对整行所有单元格统一补 `left/right`，导致内部列线也可能被套上粗边，破坏“只增强最外圈边框”的目标。

#### 设计

保留现有“根据原表格抽取边框模板”的思路，但修改边框施加范围：

- `top`：仍作用于首行全部单元格
- `bottom`：仍作用于末行全部单元格
- `left`：只作用于每行第一个单元格
- `right`：只作用于每行最后一个单元格

这样可以继续满足被切开的 `15.1 / 15.2` 需要恢复外圈边框的目标，同时不再污染内部竖线。

#### 成功结果

- 表格最外圈边框完整
- 内部列线保持原状
- 不再出现整行每个单元格都带左右粗边的副作用

### 3. 导出块空段语义回退

#### 问题

当前 `_build_document_blocks()` 把“前一个 block 不是首块”直接等同于“需要插空段”，导致同一 `section` 内的段落与表格之间也被统一插入空段。这改变了旧版导出文档的版式语义。

#### 设计

回退到旧语义：

- 同一 `section` 内只输出真实段落和真实表格
- 不主动在 `section` 内部添加空段
- 只在“保留下来的 section 与下一个保留下来的 section 之间”补一个空段

这里的“保留下来的 section”指经过空段过滤、表格清洗和修订历史过滤后仍有输出内容的 section。

#### 成功结果

- 单个 section 的内部版式与旧行为一致
- 多 section 导出仍有必要的分隔空段
- 不再新增全局性版式松散问题

### 4. Annex 修订历史过滤改为联合判定

#### 问题

当前版本导出对修订历史表的识别过宽，只要表头近似包含 `Date` 与 `Brief` 就可能删表，像 `Date | Briefing note | Value` 这种正常 Annex 表也存在误删风险。

#### 设计

将修订历史过滤改成**标题驱动的联合判定**：

1. 先遇到 `History of Revision` 标题
2. 才进入“待检查紧邻表格”的状态
3. 只检查该标题后面紧邻的第一个有效表格
4. 该表还要满足更严格的修订历史表头条件，才真正删除
5. 如果紧邻的不是修订表，则立即清掉状态，不继续影响后续表格

这个设计确保：

- 没有标题锚点时，不能只凭表头关键词删表
- 普通 Annex 表即便带 `Date`、`Briefing` 等词，也不会被孤立误删

#### 成功结果

- `Annex.docx` 中真正的修订历史标题和修订历史表被去掉
- 正常 Annex 内容表保留

## 模块改动边界

### [cleaning.py](O:/tuv-tools/src/tuv_tools/core/splitter/cleaning.py)

负责：

- `run` 内 metadata 前缀的精确裁剪
- 外圈边框施加范围修正

不负责：

- 条款识别规则调整
- Annex 修订历史语义判断

### [exporting.py](O:/tuv-tools/src/tuv_tools/core/splitter/exporting.py)

负责：

- section 间空段语义恢复
- 基于标题上下文的修订历史过滤

不负责：

- 表格内容级 metadata 清洗细节
- 表格边框结构修补

### [test_splitter.py](O:/tuv-tools/tests/test_splitter.py)

负责：

- 锁住这 4 个问题的回归边界

不负责：

- 扩展为大规模 splitter 全量回归套件

## 测试设计

### 单元测试

只补与本次问题直接对应的最小集合：

1. **前缀裁剪测试**
   - 覆盖同一段或同一 `run` 内 metadata + 正文混排
   - 断言 metadata 前缀被删
   - 断言真实测试正文保留

2. **左右外边框范围测试**
   - 覆盖双列或多列表格
   - 断言首列单元格才有 `left`
   - 断言末列单元格才有 `right`
   - 断言内部列不新增左右粗边

3. **空段语义测试**
   - 覆盖单 section 多段落
   - 覆盖段落 + 表格
   - 覆盖多 section 输出
   - 断言空段只存在于 section 间

4. **修订历史联合判定测试**
   - 有标题 + 紧邻修订表时会删除
   - 有标题但后续不是修订表时不删除
   - 普通 Annex 表头带 `Date/Briefing` 时不删除

### 真实样本验证

仅使用当前这轮已确认的真实样本，不扩大样本面：

- `19.112`
  - `Equipment / sample ID` 前缀去掉
  - `tests specified in Cl. 11 ...` 保留

- `15.1 / 15.2`
  - 最外圈边框正确
  - 内部列线不被加粗

- `Annex.docx`
  - 修订历史标题和修订历史表去掉
  - 正常 Annex 内容保留

## 错误处理与回滚边界

### 回滚原则

如果某项修复开始影响真实测试内容或正常 Annex 内容，优先收窄新逻辑，不接受通过放宽匹配范围来“修更多东西”。

### 具体边界

- 如果前缀裁剪导致格式丢失超预期，退回到“只改文本节点、不重建 run”的更保守实现
- 如果修订历史联合判定仍误删正常表，继续收窄到“标题 + 紧邻 + 严格表头”三条件同时成立才删除
- 不接受为了修复这 4 个问题去修改条款识别主规则或扩大清洗规则配置

## 验收标准

本轮完成标准只有两类：

1. 相关单测补齐并通过
2. 现有真实 DOCX 样本导出结果符合预期

不以更多历史文档回归覆盖作为本轮验收前置条件。

## 实施顺序建议

1. 先修 `run` 内前缀裁剪与对应单测
2. 再修外圈左右边框施加范围与对应单测
3. 回退导出块空段语义并补测试
4. 最后把 Annex 修订历史过滤改成联合判定并补测试
5. 跑 `tests/test_splitter.py`
6. 用当前真实样本做导出验证

这样排序的原因是：

- 前两项是当前真实文档最直接的错误来源
- 第三项是确定性版式回归
- 第四项需要结合版本导出路径最后统一验证
